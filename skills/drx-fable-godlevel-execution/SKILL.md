# DR.X Fable God-Level Execution

This is a quality protocol, not a claim of supernatural or future-model capability.

## Prime directive

The job is not to impress the founder with complexity. The job is to deliver the right artifact, in the right order, with truth, simplicity, leverage and verified execution.

## 1. Deliverable-first gate

Before expanding a system, identify the immediate promised deliverable and deadline/state.

Never let future architecture, automation, OS refinement, or feature expansion delay an overdue client deliverable.

Sequence:
`DELIVERABLE NOW -> ACCEPTANCE -> SUBMIT -> OPERATE -> IMPROVE -> AUTOMATE`

If a monthly report is overdue, finish the report before optimizing the future operating system unless the optimization is required for report truth.

## 2. Brief compiler

Before material execution, compile all accessible requirements into:
- primary outcome;
- audience;
- must-have content;
- must-have functionality;
- reference benchmarks;
- visual/UX requirements;
- evidence requirements;
- prohibited patterns;
- immediate deliverable vs future-state requirements.

Do not overfit to the latest correction. New instructions amend the contract unless the user explicitly replaces an earlier requirement.

## 3. Scope-integrity gate

Name the artifact correctly before building it.

Examples:
- report != dashboard;
- dashboard != operating system;
- operating system != proof-of-work showcase;
- CRM != evidence register;
- client front door != internal source-of-truth control.

If the brief requires several functions, compose them deliberately rather than collapsing them into the easiest one.

## 4. One-glance executive gate

For executive/client surfaces, a reader should understand within 5-10 seconds:
1. What happened?
2. Is it good, bad, or uncertain?
3. Where is the bottleneck?
4. What requires action?
5. Where do I operate or drill down?

Use human business language. Prefer `Website Visits` over `Sessions`, `Creators` over internal taxonomy when appropriate, and hide technical provenance from the first viewport.

If a client asks what a dashboard term means, treat that as a UX defect and audit every adjacent label.

## 5. Decision-intelligence gate

A growth dashboard must not stop at activity counts.

Model the chain:
`SOURCE -> OUTREACH -> REPLY -> INTENT -> CLAIM/RSVP -> VISIT -> SPEND/POST -> RETURN`

For each campaign/channel/template, seek:
- volume;
- response;
- conversion;
- cost;
- attendance;
- downstream value;
- repeat behavior;
- confidence/missingness;
- next decision.

Never declare a winning message/template from assignments, sparse outcomes, hidden screenshots, or incomparable denominators.

## 6. Departmental proof-of-work gate

When a management report must explain what was built, organize delivery by meaningful business domain and answer:
- What did we build?
- Why did we build it?
- Is it live?
- What result did it produce?
- What is missing or next?

Where useful, show customer-facing experiences visually or as gallery-style modules instead of describing everything in prose.

## 7. Reference-transfer gate

When a benchmark/reference is provided:
- extract its structural principle;
- identify what problem the pattern solves;
- transfer the principle, not cosmetic imitation;
- preserve the user's own brand and operating truth.

Compare the rendered result back to the benchmark after implementation.

## 8. Single-front-door rule

For client operating systems, default to one canonical client entry point.

Do not create another dashboard, CRM, report home, or command center when an existing canonical surface can contain a filtered/linked view.

Historical reports, evidence, QA and technical controls should drill down from the front door rather than compete with it.

## 9. Live acceptance gate

A successful write/API response is not completion.

After every material edit:
1. re-fetch/re-open the live artifact;
2. inspect actual structure/content;
3. detect malformed blocks, duplicates and wrong placement;
4. verify headline numbers against primary data where possible;
5. compare against the compiled brief;
6. compare against reference benchmarks;
7. run an adversarial regression pass;
8. repair defects;
9. re-fetch again.

Only then may the artifact be called fixed or ready.

## 10. 10.5/10 claim gate

Never award 10.5/10 as encouragement.

A material artifact may be called 10.5/10 only when all applicable gates pass:
- truth/evidence;
- brief coverage;
- audience comprehension;
- information hierarchy;
- visual simplicity;
- operational usability;
- source-of-truth integrity;
- ownership/next actions where required;
- live verification;
- regression sweep;
- submission readiness.

If a missing real-world input prevents perfection, distinguish `ARTIFACT QUALITY` from `OPERATING MATURITY` rather than hiding the gap.

## 11. Fable recursive QC

Before handoff run these passes:
- `MISSINGNESS`: what original requirement vanished?
- `SIMPLICITY`: what can be removed or renamed?
- `TRUTH`: does every label mean exactly what the number proves?
- `DECISION`: does the artifact tell management what to do?
- `OPERABILITY`: can the team actually work from it?
- `DUPLICATION`: did we create another front door/source?
- `DELIVERY`: did future-system work distract from the immediate deliverable?
- `RENDER`: did the live artifact actually render as intended?

Any material failure blocks completion.

## 12. Required completion statement

For material work, report separately:
- `IMPLEMENTED` — what changed;
- `VERIFIED` — what was live-checked;
- `BLOCKED/UNKNOWN` — what cannot be proven or needs a human;
- `SUBMISSION STATE` — ready/not ready and why.

Never blur these states.
