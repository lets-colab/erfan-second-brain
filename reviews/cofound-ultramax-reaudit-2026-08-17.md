## 4. What evolved later and survives

These later mechanisms remain coherent with the original human problem:

### Visual Action Branches
Turns roadmap/outcome logic into navigable routes rather than task lists.

### Detour
`Blocked != stopped.` A blocked route should surface other executable paths toward the same destination.

### ROOM / MAP / FOCUS / ASK
The earlier THE ROOM / MY VIEW / AI concepts converged into four cognitive modes:
- ROOM — shared orientation;
- MAP — navigation;
- FOCUS — personal action;
- ASK — natural-language access/control.

### Replay / Decision -> Outcome Memory
Preserves what was known, assumed, chosen, spent, executed, observed and learned without rewriting the past using hindsight.

### Pre-Live
Explores future branches as simulation, not prediction.

### Correction-first capture
The system should infer/propose state changes from meetings and tools for humans to confirm/correct, because manual maintenance threatens adoption and truth freshness.

### Epistemic graph relationships
Dependencies, strategic hypotheses, observed associations, historical sequence and simulations must not be visually conflated with proven causality.

### Multi-business environment
CO.FOUND can contain multiple company/venture spaces while sharing permitted founders, capabilities, resources and relationships.

## 5. User corrections that must now be treated as first-class product intent

### A. The origin is a three-founder OS
The concept was first for Erfan, Sayem and Fahim operating together. LastBench is the first company-space/test environment, not the permanent umbrella identity.

### B. Learning-through-work is core
The product should help a person who does not know how to execute a meaningful task identify the capability gap, learn, practice, apply and produce evidence of capability through real work.

This is not merely a future Class A feature. It is a CO.FOUND product principle.

### C. Motivation/game feel is core
The product should feel rewarding and compelling through immediate feedback, short missions, visible state change, route unlocks, blocker removal, milestone activation, skill growth and meaningful celebration.

Do not frame this as medical ADHD treatment or deliberately harmful addiction. Design for neuroinclusive low-cognitive-load execution and motivational scaffolding.

### D. CO.FOUND is the environment
CO.FOUND does not sit under Co.Lab.

Correct hierarchy:
1. CO.FOUND — operating intelligence environment;
2. Founder Intelligence — reasoning/navigation/memory engine;
3. ROOM / MAP / FOCUS / ASK + Replay / Pre-Live / Learning / Momentum;
4. Co.Lab, LastBench, Class A and future ventures as company spaces;
5. integrated source systems underneath.

## 6. Reconciled simplicity laws

Two earlier simplicity models are both useful because they govern different dimensions.

### Comprehension law
`3 seconds -> 1 minute -> depth`

- 3 seconds: understand state/attention;
- 1 minute: understand what changed, why and what needs action;
- depth: inspect evidence, graph, history, scenarios and operations.

### MAP disclosure law
`1 destination -> up to 3 routes -> depth`

- one destination visible first;
- no more than three primary routes at first level;
- deeper branches appear only on interaction.

These are complementary, not contradictory.

## 7. Meeting Mode correction

The earlier Board / Founder Meeting Mode was too implicit in the later canonical architecture.

Final interpretation:
- do not add another permanent top-level navigation item;
- preserve `MEETING MODE` as a contextual state of ROOM;
- before meeting: changes, blockers, money, unresolved decisions, previous commitments;
- during: decisions/notes/owners;
- after: decision -> action -> owner -> deadline -> graph/history update.

This preserves the original three-founder ritual without increasing navigation complexity.

## 8. Learning status correction

The v2 canonical file placed Capability / Skill Intelligence mainly in `ARCHITECT_NOW_UI_LATER` and full Class A Skill Quests in `DEFERRED`.

That is only partly correct.

Revised distinction:

### CORE PRINCIPLE NOW
- work should expose capability gaps;
- learning should be contextual to live work;
- applied skill evidence should be recordable;
- company progress and human capability should both be visible outcomes.

### V0B MINIMUM TEST
At least one real capability-gap flow should be tested:

`mission -> cannot/do-not-know -> micro guidance/learning -> practice -> apply -> result -> skill evidence`

### DEFERRED

- large Class A content system;
- rich skill tree;
- certifications;
- advanced capability inference.

This prevents a core product promise from being postponed so long that it is never validated.

## 16. Experiment logic

The product must be compared against the existing founder workflow, not against imagination.

Test the same questions in both systems:
- where are we going?
- what is blocked?
- what should I do?
- what changed?
- what money is actually available/committed?
- why did we make decision X?
- what other route is executable?
- if I do not know how to execute this mission, can the system help me become capable enough to do it?

Measure:
- speed;
- accuracy;
- agreement between founders;
- decision change/acceleration;
- missed commitments;
- maintenance burden;
- return behavior;
- capability gained/applied;
- whether meaningful progress feels motivating enough to return without coercive mechanics.

## 17. Commercial conclusion

No new broad SaaS green light is justified by this audit alone.

Preferred path remains:
`LastBench real pilot -> evidence -> service-assisted external operating teams -> distinguish consulting value from product value -> recurring retained paid behavior -> only then larger SaaS investment`.

The fact that Co.Lab can act as an implementation partner does **not** make CO.FOUND a sub-product of Co.Lab. Runtime/product hierarchy and go-to-market/origin relationship are separate concepts.
